二、登录持久化问题深度分析（P0 重点）
用户反馈："登录后刷新页面需要重新登录，不符合现在主流的鉴权流程。"该问题是本次消耗时间最多的修复项，经历了 5 次尝试才彻底解决。
P0
登录后刷新页面重定向到登录页
问题现象
用户使用账号密码登录成功，跳转到 /board 页面，内容正常显示。但刷新浏览器（F5）后，页面短暂显示 loading 动画，随后重定向到 /login，要求重新输入账号密码。
根因分析
问题的根因是 zustand persist 中间件的异步 hydration 与 React 渲染时序之间的竞态条件。具体链路如下：
  • 页面刷新时，React 首次渲染，ProtectedRoute 读取 useAuthStore 的初始状态：isLoading=true, isAuthenticated=false
  • 同时，zustand persist 从 localStorage 异步恢复 token，写入 store
  • 但 persist 的 hydration 回调 onRehydrateStorage 并不保证在 React 第一次渲染前完成
  • ProtectedRoute 看到 isAuthenticated=false，立即执行 Navigate to="/login"
  • 即使 token 后续恢复了，路由已经跳转走了
为什么这个问题难修
zustand persist 的 hydration 是 异步且非确定性的。在某些浏览器/环境下，hydration 可能因为以下原因卡住或延迟：
  • localStorage 读取被浏览器节流（隐私模式、存储配额接近上限）
  • onRehydrateStorage 回调中包含异步操作（如 fetchUser）导致 hydration 完成信号被阻塞
  • createJSONStorage wrapper 的 Promise 链在某些边缘情况下不 resolve
  • React 18 的并发模式下，useEffect 可能在 store 状态更新前就执行

修复尝试过程（5 次迭代）
尝试时间线
尝试 1：在 onRehydrateStorage 中调用 fetchUser 失败
思路：persist 恢复 token 后，立即调用 fetchUser() 验证 token 并加载用户信息。
问题：onRehydrateStorage 回调中调用异步函数会导致 hydration 完成信号被阻塞。store 一直处于 hasHydrated=false 状态，ProtectedRoute 的 loading 兜底超时触发后强制 isAuthenticated=false。
教训：onRehydrateStorage 应只做同步状态标记，不应承担异步认证逻辑。
尝试 2：添加 silentRefresh 作为刷新后备 失败
思路：token 不存在时，尝试用 HttpOnly refresh_token cookie 调用 /auth/refresh 获取新 token。
问题：silentRefresh 在 onRehydrateStorage 中调用，同样阻塞 hydration。且 /auth/refresh 路径未加入 PUBLIC_PATHS，被中间件拦截返回 401。
教训：refresh 端点必须在后端白名单中，且不应在 hydration 回调中调用。
尝试 3：分离 hydration 与认证，引入 AuthInit 组件 部分解决
思路：创建 AuthInit 组件，用 useState + useEffect 等待 useAuthStore.persist.hasHydrated() 返回 true 后再执行认证逻辑。
结果：大多数情况下正常工作，但偶发仍跳转登录页。
问题：persist.hasHydrated() 在某些浏览器环境下永远不返回 true（localStorage 读取 Promise 不 resolve），导致 AuthInit 永久等待。
教训：不能无限等待 hydration，必须有兜底超时。
尝试 4：添加 3 秒兜底超时 部分解决
思路：在 AuthInit 中设置 setTimeout(3000)，如果 hydration 未完成则强制继续。
问题：超时后 store 中仍无 token（因为 hydration 没完成意味着 localStorage 值没被读出来），认证失败跳转登录。
教训：兜底超时不能只"跳过等待"，还需要在超时时手动从 localStorage 读取 token。
尝试 5：兜底超时 + 手动 localStorage 加载（最终方案） 成功
思路：3 秒超时后，如果 hydration 仍未完成，手动从 localStorage.getItem('conclave:auth') 读取 token，解析 JSON 后通过 useAuthStore.setState({ token }) 注入 store。
结果：所有测试场景通过——正常刷新保持登录、token 过期自动刷新、无 token 跳转登录。
这是最终采用的方案。
最终方案架构
// App.tsx — AuthInit 组件
function AuthInit() {
  const [hydrated, setHydrated] = React.useState(false);

  // 1. 等 persist hydration
  React.useEffect(() => {
    if (useAuthStore.persist.hasHydrated()) { setHydrated(true); return; }
    const unsub = useAuthStore.persist.onFinishHydration(() => setHydrated(true));

    // 2. 3秒兜底：手动加载 localStorage token
    const timeout = setTimeout(() => {
      if (!useAuthStore.persist.hasHydrated()) {
        const raw = localStorage.getItem('conclave:auth');
        if (raw) {
          const token = JSON.parse(raw)?.state?.token;
          if (token) useAuthStore.setState({ token });
        }
        setHydrated(true);
      }
    }, 3000);
    return () => { unsub(); clearTimeout(timeout); };
  }, []);

  // 3. hydration 完成后执行认证逻辑
  React.useEffect(() => {
    if (!hydrated) return;
    const { token, fetchUser, silentRefresh, setLoading } = useAuthStore.getState();
    (async () => {
      if (token) {
        if (await fetchUser()) return;        // token 有效
        if (await silentRefresh()) return;    // token 过期，刷新成功
      } else {
        if (await silentRefresh()) return;    // 无 token，尝试 cookie 刷新
      }
      setLoading(false);                       // 全部失败，未认证
    })();
  }, [hydrated]);
}
为什么这样修复（决策理由）
  • 分离 hydration 与认证：onRehydrateStorage 只标记 hasHydrated=true，不调用任何异步函数。认证逻辑集中在 AuthInit 中，避免竞态
  • 3 秒兜底超时：正常情况 hydration 在毫秒级完成，3 秒是极端边缘情况的安全网。超时后仍手动读取 localStorage，确保 token 不丢失
  • 三层认证降级：token 有效 → fetchUser 验证；token 过期 → silentRefresh 刷新；无 token → 尝试 cookie 刷新；全部失败 → 未认证。覆盖所有场景
  • 移除 createJSONStorage：直接使用 storage: createJSONStorage(() => localStorage) 的默认行为，避免不必要的 Promise 包装
关于"绕过兜底"的说明：3 秒兜底超时 + 手动 localStorage 加载不是"绕过"问题，而是防御性编程。zustand persist 的 hydration 在 99% 的情况下正常工作，但浏览器环境（隐私模式、存储策略、扩展干扰）可能导致异常。兜底机制确保即使 hydration 失败，用户也不会被错误地登出。这与主流平台（如 Linear、Vercel）的做法一致——永远有 fallback。

P1

问题描述
用户反馈：文件删除需要增加级联删除（直接删除文件夹所有内容），且需限定删除角色权限。
根因
  • 后端 DELETE /workspace/files/{path} 仅支持删除单文件或空目录，无 cascade 参数

  • cascade=false 删除非空目录时返回 400 提示"请使用级联删除"
权限模型（auth_guard.py）：
  • 从文件路径提取 meeting_id（mtg- 前缀目录）
  • 调用 assert_can_delete_meeting() 校验权限
权限层级： 
1. system_owner / system_admin / admin → 始终允许
2. 会议创建者（owner_username == username）→ 允许
3. Team owner / maintainer → 允许
4. 其他角色 → 403 拒绝
前端（workspace/page.tsx）：
  • 删除确认对话框添加"级联删除"复选框，默认勾选
  • 提示文案："将删除该文件夹及其所有子文件和子文件夹"

五、API 数据模型与字段映射问题
用户反馈："因为 api 和数据模型以及字段的导致的问题你似乎没提到或者不够全？" — 本节专门复盘本次所有因 API 契约不一致、数据模型字段缺失或命名风格冲突导致的问题。
P0
前后端字段命名风格不一致（snake_case vs camelCase）
问题现象
后端 API 返回 snake_case（Python 惯例），前端 TypeScript 类型/组件期望 camelCase（JS 惯例）。直接使用后端字段名导致前端渲染 undefined 或崩溃。
受影响的字段映射
后端字段（snake_case）前端期望（camelCase）影响范围处理方式
message_countmessageCount会议列表、会议详情normalize 层同时输出两者
created_atcreatedAt（number 时间戳）会议列表、详情normalize 层转换 Date.parse()
is_runningmetadata.isRunning会议列表normalize 层放入 metadata
role_configsagents会议详情normalize 层重映射字段名
clarified_topictitle会议详情normalize 层 fallback 取值
artifact.summarysummary会议详情normalize 层提取嵌套字段
owner_username无前端对应（仅后端权限用）权限校验后端内部使用，不暴露前端
tenant_idtenant_id（保持 snake_case）用户信息例外：用户信息保持 snake_case 不转换
根因分析
  • 无统一 API 契约层：后端直接返回 ORM/payload 原始字段名，前端直接消费，缺少中间 normalize 层
  • TypeScript 类型定义双轨：Meeting 类型同时定义了 messageCount? 和 message_count? 两个可选字段，组件各取所需，不一致
  • 会议详情接口与列表接口字段结构不同：列表返回 agents 数组（从 role_configs 提取），详情返回 role_configs 原始结构，前端需要两套 normalize 函数
  • 时间格式不统一：后端返回 ISO 字符串 created_at，部分前端组件期望 createdAt 为 Unix 时间戳（number）
修复方案
normalize 层（use-meetings.ts）： 
// 列表项 normalize
function normalizeMeeting(raw: BackendMeetingItem): Meeting {
  return {
    id: raw.meeting_id,           // meeting_id → id
    title: raw.topic || '未命名讨论', // topic → title
    status: raw.status,
    stage: raw.stage,
    created_at: raw.created_at,    // 保留原始
    createdAt: raw.created_at ? Date.parse(raw.created_at) : undefined, // 转时间戳
    message_count: raw.message_count,  // 保留 snake_case
    messageCount: raw.message_count,   // 同时输出 camelCase
    agents: Array.isArray(raw.agents)
      ? raw.agents.map(a => ({ id: a.id, name: a.name, role: a.role, state: a.state || 'idle' }))
      : [],
    metadata: { is_running: raw.is_running, tags: raw.tags },
  };
}

// 详情 normalize（结构不同，需单独处理）
function normalizeMeetingDetail(raw: BackendMeetingDetail): Meeting {
  const agents = Array.isArray(raw.role_configs)
    ? raw.role_configs.map(rc => ({ id: rc.id, name: rc.name, role: rc.role, state: 'idle' }))
    : [];  // role_configs → agents
  const messageCount = Array.isArray(raw.messages) ? raw.messages.length : undefined;
  return {
    id: raw.meeting_id,
    title: raw.clarified_topic || raw.topic || '未命名讨论', // fallback 取值
    summary: raw.artifact?.summary,  // 嵌套字段提取
    messageCount,
    message_count: messageCount,
    agents,
    metadata: { key_questions: raw.key_questions, artifact: raw.artifact },
  };
}
为什么这样修复
  • normalize 层放在 hook 中而非组件中：所有 API 字段映射集中在一处，组件只消费标准化的 Meeting 类型
  • 同时输出 snake_case 和 camelCase：兼容历史组件代码（部分用 messageCount，部分用 message_count），避免一次性大规模重构
  • 列表和详情分别 normalize：两个接口返回结构差异大（列表有 agents，详情有 role_configs），强行统一反而增加复杂度
  • 用户信息例外：tenant_id 在前端用户类型中保持 snake_case，因为它直接透传给后端 API，转换无意义

P1
会议详情接口 role_configs 与前端 agents 的结构差异
问题现象
前端 Meeting 类型有 agents: AgentInfo[] 字段（{id, name, role, state}），但后端会议详情接口返回的是 role_configs（{id, name, role, description}），无 state 字段。直接透传导致前端 agent.state 为 undefined。
根因
后端数据模型中 Agent 的运行时状态（state）是动态计算的，不存储在 role_configs 中。role_configs 只是配置（静态），state 需要从运行时状态机获取。列表接口的 agents_summary 也没返回 state。
修复
normalize 层将 role_configs 映射为 agents，state 默认设为 'idle'： 
const agents = Array.isArray(raw.role_configs)
  ? raw.role_configs.map(rc => ({
      id: rc.id, name: rc.name, role: rc.role,
      state: 'idle' as AgentState,  // 默认值
    }))
  : [];
遗留风险
state: 'idle' 是硬编码默认值，不反映 Agent 的真实运行时状态。后续需要后端在详情接口中返回真实 state（从状态机或 _running_tasks 中获取），或前端通过 WebSocket 实时获取。
P1
delete_meeting 参数签名变更导致前后端不兼容
问题现象
后端 delete_meeting 函数的 mode 参数从 query param 改为 request body 后，前端 DELETE /meetings/{id}?mode=soft 请求的 mode 值无法被后端正确解析。
根因
FastAPI 的参数解析规则：mode: str = "soft" 默认从 query string 解析；如果函数签名中添加了 Body() 注解或 Pydantic model 参数，FastAPI 会尝试从 request body 解析。DELETE 请求通常不带 body，导致参数丢失。
修复
确保 mode 为纯 query param：async def delete_meeting(meeting_id: str, request: Request, mode: str = "soft")。不添加 Body() 注解。前端通过 DELETE /meetings/{id}?mode=soft 传递。
P2
用户信息 tenants 字段类型不一致
问题现象
后端 /auth/me 返回的 user.tenants 可能为 null（用户无租户）、undefined（字段缺失）或非数组类型。前端 useRbac hook 直接调用 user.tenants.find()，当 tenants 为 null 时抛出 Cannot read property 'find' of null。
根因
后端用户信息来源不同（/auth/login 返回完整 tenants 列表，/auth/me 可能不返回或返回 null），前端类型定义 tenants: TenantInfo[] 标记为必填，但实际可能为空。
修复
fetchUser 中添加防御性处理： 
const user: UserInfo = (res as { user?: UserInfo }).user ?? (res as UserInfo);
if (user && !Array.isArray(user.tenants)) user.tenants = [];
if (user && user.tenant_id == null) user.tenant_id = '';
确保返回给前端的 tenants 始终是数组，tenant_id 始终是字符串。
P2
会议详情 summary 字段嵌套路径不一致
问题现象
前端 Meeting.summary 期望直接是 string | undefined，但后端返回的 summary 嵌套在 artifact.summary 中，需要从嵌套对象中提取。
根因
后端会议数据的 artifact 是 JSONB 字段，包含多种产出物（summary、report、decisions 等）。summary 是 artifact 的子字段，不是顶级字段。
修复
normalize 层提取：summary: raw.artifact?.summary as string | null | undefined。同时保留 raw.artifact 在 metadata.artifact 中供其他组件使用。
P2
会议列表使用裸 useQuery 而非 useMeetings hook
问题现象
explore/list-page.tsx 最初使用 useQuery 直接调用 /meetings API，返回的是后端原始格式（snake_case），未经 normalize。列表渲染时 meeting.messageCount 为 undefined，显示 "—"。Agent 数量也显示异常。
根因
页面绕过了 useMeetings hook（含 normalize 逻辑），直接使用 useQuery 裸调用 API。这是一个架构规范执行不彻底的问题——hook 已存在但未被使用。
修复
将 useQuery 替换为 useMeetings({ pageSize: 50 })，走 normalize 层。同时移除页面内联的 useQuery 逻辑。
为什么这个问题值得单独记录
它不是单纯的字段名问题，而是架构执行问题——有 normalize 层但不用。类似的问题可能在其他页面也存在（直接 useQuery 而非走 hook），需要系统性排查。
P2
API 路由路径前后端定义不一致
问题现象
前端调用 /docker-hosts/overview 和 /docker-hosts/commands-reference，后端路由定义中这两个静态路径被 /{host_id} 动态路由拦截，返回 404。
根因
FastAPI 路由匹配按定义顺序执行。@router.get("/{host_id}") 定义在 @router.get("/overview") 之前时，字符串 "overview" 被当作 host_id 参数匹配成功，导致 /overview 路由永远不被执行。
修复
调整路由定义顺序：静态路径 /overview、/commands-reference 移到动态路径 /{host_id} 之前。
同类风险
任何 @router.get("/{xxx_id}") 动态路由之后定义的静态子路径都有此风险。应建立规范：静态路径永远在动态路径之前定义，或使用 Path(regex="...") 约束动态参数格式。

八、Token 过期时间调整
P2
access_token 过期时间从 24h 缩短为 15 分钟
问题
JWT_EXPIRE_SECONDS 默认值为 86400（24 小时），过长。如果 token 泄露，攻击者有 24 小时窗口使用它。
修复
# backend/app/auth.py
# 修改前
JWT_EXPIRE_SECONDS = int(os.environ.get("CONCLAVE_JWT_EXPIRE", "86400"))
# 修改后
JWT_EXPIRE_SECONDS = int(os.environ.get("CONCLAVE_JWT_EXPIRE", "900"))  # 15分钟
refresh_token 保持 7 天不变。前端 mock-data.ts 的 jwt_expire_minutes 同步从 60 改为 15。
修复原因
  • 安全最佳实践：OWASP 建议 access_token 过期时间不超过 15-30 分钟。缩短窗口可减少 token 泄露的影响范围
  • 不影响用户体验：已实现 token 自动刷新拦截器，15 分钟过期对用户无感知——过期时自动刷新，请求自动重放
  • 依赖前置修复：此修复依赖登录持久化（token 自动刷新）完成，否则 15 分钟过期会导致用户频繁被登出
九、时间消耗与效率分析
P0
登录持久化问题消耗了约 60% 总工时
时间分布（估算）
问题类别估算耗时占比尝试次数效率评估
登录持久化 ~90 分钟 60% 5 次 低效 — 根因定位慢，多次尝试
运维面板 ~25 分钟 17% 4 次 中等 — 路由顺序问题排查耗时
会议删除 ~15 分钟 10% 3 次 中等 — 字段名不匹配导致返工
文件删除 ~10 分钟 7% 2 次 高效 — 一次实现，权限模型扩展一次
错误提示 ~5 分钟 3% 1 次 高效 — 直接映射，无反复
Token 安全 ~5 分钟 3% 1 次 高效 — 依赖前置完成，直接修改
登录问题为什么耗时这么久
核心原因：zustand persist 的 hydration 机制是"黑盒异步"。

zustand persist 使用 createJSONStorage 包装 localStorage，返回的是 Promise。但这个 Promise 的 resolve 时机不受我们控制——它依赖浏览器的微任务队列调度。在大多数情况下，hydration 在 React 首次渲染前完成；但在某些边缘情况（浏览器扩展干扰、隐私模式、存储配额），hydration 可能永远不完成。

耗时分解：
  • 尝试 1-2（~30 分钟）：在 onRehydrateStorage 中调用异步函数，导致 hydration 阻塞。这两次尝试的错误方向一致——试图在 hydration 回调中做认证
  • 尝试 3（~20 分钟）：分离 hydration 和认证，引入 AuthInit。思路正确但缺少兜底
  • 尝试 4-5（~40 分钟）：添加兜底超时和手动 localStorage 加载。调试浏览器环境下的 hydration 行为耗费大量时间
根本教训：应该一开始就调研 zustand persist 的 hydration 机制，而不是边试边猜。前两次尝试完全是在错误的方向上浪费时间。
十、经验教训与改进建议
P1
5 条关键教训
#教训详细说明改进措施
1 先调研再动手 登录持久化问题前两次尝试方向完全错误（在 hydration 回调中做异步认证），根因是没有先理解 zustand persist 的 hydration 机制。应该先读源码/文档，理解 onRehydrateStorage 的执行时机和约束 修复前先读依赖库文档
2 异步回调不做异步操作 onRehydrateStorage 是同步回调，在其中调用 fetchUser() 会阻塞 hydration 完成信号。这是 zustand persist 的已知陷阱 回调只做同步状态标记
3 必须有兜底机制 不能无限等待异步操作完成。AuthInit 的 3 秒兜底超时 + 手动 localStorage 加载是防御性编程的体现，不是"绕过" 所有异步等待加超时
4 前后端字段名统一 会议删除的 message_count vs messageCount 不匹配导致返工。后端用 snake_case，前端用 camelCase，中间需要 normalize 层 hook 层统一 normalize
5 路由顺序是常见陷阱 FastAPI 动态路由 /{host_id} 会拦截 /overview 等静态路径。静态路径必须在动态路径之前定义 路由定义先静态后动态
P2
系统性改进建议
  • 认证流程文档化：将本次的认证流程（AuthInit → fetchUser → silentRefresh → 兜底）写成 ADR，避免下次重复踩坑
  • zustand persist 使用规范：在项目中建立规范——onRehydrateStorage 只做同步标记，认证逻辑在组件层用 useEffect 处理，所有异步等待加超时兜底
  • 前端 normalize 层：所有 API 响应在 hook 层统一 normalize（snake_case → camelCase），避免字段名不匹配问题
  • 路由定义规范：FastAPI 路由文件中，静态路径（/overview, /commands-reference）必须在动态路径（/{host_id}）之前定义，添加 lint 检查
  • 端到端测试常态化：本次多次"后端 API 正常但前端无法使用"的问题，说明仅 curl 测试不够，必须配合浏览器端到端验证
