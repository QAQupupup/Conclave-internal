## A. 五个问题的产品方案

---

### 问题 1：会议删除 — 权限、关联资源、软删除性能

#### 1.1 用户故事

- **US-1.1** 作为会议创建者，我希望能删除自己创建的测试会议/废弃会议，避免列表被噪音淹没。
- **US-1.2** 作为租户管理员，我希望能彻底清除包含敏感信息的会议记录，确保数据不残留。
- **US-1.3** 作为普通参与者，我不应能删除别人创建的进行中会议。
- **US-1.4** 作为系统，当软删除数据量达到万级以上时，列表查询和 JSON 解析不应明显变慢。

#### 1.2 产品决策

**三级删除模型：**

```
┌─────────────┐     软删除      ┌─────────────┐     归档       ┌─────────────┐
│   活跃会议   │ ─────────────→ │  回收站(30天) │ ─────────────→ │   归档库     │
│  (active)   │                │  (deleted)   │                │ (archived)  │
└─────────────┘                └─────────────┘                └─────────────┘
       ↑                              │                              │
       │        恢复(30天内)           │        硬删除/自动清理        │
       └──────────────────────────────┘──────────────────────────────┘
```

**决策一：删除权限模型（RBAC 简化版）**

| 角色 | 软删除自己的会议 | 软删除他人会议 | 硬删除 | 恢复 |
|------|----------------|--------------|--------|------|
| 会议创建者 (owner) | ✓ | ✗ | ✗ | ✓（仅自己删除的） |
| 租户管理员 (admin) | ✓ | ✓ | ✓（需二次确认） | ✓ |
| 普通参与者 (member) | ✗ | ✗ | ✗ | ✗ |
| 系统 (system) | — | — | 自动清理过期回收站 | 自动恢复崩溃会议 |

- 权限判定逻辑：`is_owner OR is_admin` 可软删除；仅 `is_admin` 可硬删除。
- running 状态的会议禁止删除（必须先暂停/中止），已有 `batch_delete_meetings` 的 failed 逻辑扩展即可。
- 硬删除需二次确认弹窗，输入会议标题前 4 字确认（防误操作）。

**决策二：关联资源处理策略**

| 资源类型 | 软删除时 | 硬删除时 | 归档时 |
|---------|---------|---------|--------|
| meetings 主记录 | status=deleted，保留 | 永久删除 | status 保持 done，标记 archive_status |
| messages | 保留 | 级联删除 | 保留（可配置冷热分离） |
| events | 保留 | 级联删除 | 保留 |
| meeting_tags | 保留 | 级联删除 | 保留 |
| meeting_aux（大字段） | 保留 | 级联删除 | 压缩后保留 |
| 图谱节点/边 | 从活跃图谱移除，保留在归档视图 | 永久删除 | 归档图谱独立展示 |
| Reports 产出物 | 保留访问入口 | 级联删除 | 保留 |
| reference_meeting_ids 引用 | 仍可被新会议引用（只读） | 引用失效需提示 | 仍可引用 |

**决策三：软删除性能优化方案**

软删除数据量上来后的性能瓶颈有三处，逐一解决：

**瓶颈 1：列表查询扫描全表过滤 `status != 'deleted'`**
- 方案：利用现有 `idx_meetings_status` 索引。当软删除占比 > 20% 时，新增**部分索引**（Partial Index）：
  ```sql
  CREATE INDEX idx_meetings_active ON meetings (created_at DESC) 
  WHERE status NOT IN ('deleted', 'archived');
  ```
- 触发条件：DBA 巡检发现软删除记录超过 5000 条时执行迁移。

**瓶颈 2：payload JSON 全量反序列化**
- 当前 `list_meetings`/`query_meetings` 对每条记录都 `json.loads(d["payload"])`，当 payload 很大（含 llm_trace）时开销显著。
- 方案：列表查询不反序列化完整 payload，改为**列表专用投影查询**，只取列表卡片需要的字段：
  ```sql
  SELECT id, topic, owner_username, status, stage, created_at, 
         payload->>'clarified_topic' AS clarified_topic,
         payload->>'artifact_summary' AS artifact_summary
  FROM meetings WHERE ...
  ```
- 完整 payload 仅在进入 Explore 详情页时加载。
- meeting_aux 已分离大字段，进一步确保 payload 主字段保持轻量（< 10KB）。

**瓶颈 3：回收站数据无限膨胀**
- 方案：**回收站自动过期清理**。软删除 30 天后，后台任务自动执行硬删除（或迁移到归档）。
- 配置项：`PURGE_DELETED_AFTER_DAYS = 30`，租户管理员可调整（7-90 天）。
- 清理任务：每日凌晨低峰期执行，每次批量处理 100 条，避免长事务锁表。

#### 1.3 交互设计

- **列表页**：每个会议卡片右上角 "⋯" 菜单增加「删除」选项（红色文字）。
- **批量操作**：多选模式下，底部操作栏出现「删除」按钮，走批量软删除。
- **回收站入口**：列表页筛选 Tab 增加「回收站」（数字角标显示待清理数量），进入回收站可「恢复」或「永久删除」。
- **硬删除确认**：弹窗显示「此操作将永久删除会议及其所有消息、事件、标签，不可恢复。请输入会议标题 `____` 以确认。」
- **Toast 提示**：删除后显示「已移入回收站，30 天后自动清理」+「撤销」按钮（5 秒内可撤销）。

#### 1.4 数据影响

- meetings 表新增字段：`deleted_at TIMESTAMP NULL`（替代 payload._deleted_at，便于索引和 SQL 查询），`deleted_by VARCHAR(100) NULL`。
- 新增数据库迁移脚本（alembic），将 payload._deleted_at 数据回填到 deleted_at 列。
- 新增 `meeting_permissions` 表或复用租户角色字段（初期用 owner_username + tenant role 判断即可，不新建表）。
- 新增后台定时任务：`purge_expired_deleted_meetings`。
- 列表查询改造：投影查询 + 部分索引（可选迁移）。

### 问题 2：归档功能

#### 2.1 用户故事

- **US-2.1** 作为长期用户，我希望 3 个月前已完成的会议自动收纳到归档区，保持活跃列表清爽。
- **US-2.2** 作为团队负责人，我希望会议能按项目/主题分类归档，方便回溯查找。
- **US-2.3** 作为用户，我创建会议时就能指定分类/简写标题，不必事后整理。
- **US-2.4** 作为用户，归档后的会议图谱仍可查看，作为组织知识沉淀的一部分。

#### 2.2 产品决策

**决策一：归档的本质定义**

归档 ≠ 删除。归档是**从活跃工作区移出到知识沉淀区**，数据完整保留、可搜索、可引用、可查看图谱，但默认不干扰日常工作列表。

归档状态独立于 deleted 状态，二者正交：

| | 活跃 (active) | 已归档 (archived) | 已删除 (deleted) |
|---|---|---|---|
| 默认列表可见 | ✓ | ✗（需切换到归档Tab） | ✗（回收站） |
| 可被 reference_meeting_ids 引用 | ✓ | ✓ | ✓（但有警告） |
| 可克隆/重跑 | ✓ | ✓（需先取消归档或直接克隆） | ✗ |
| 图谱可见 | 活跃图谱 | 归档图谱（独立视图） | 不可见 |
| 数据完整性 | 完整 | 完整（可冷热分离） | 完整（30天窗口） |
| 自动触发 | — | N 天未访问 | 30天后硬删除 |

**决策二：归档触发方式（手动 + 自动双轨）**

**自动归档规则（默认开启，可配置）：**
- 时间规则：done/aborted 状态的会议，**超过 90 天未被访问**（访问定义：进入详情页/被新会议引用/被克隆），自动归档。
- 数量规则：活跃列表超过 100 条已完成会议时，最早完成的自动归档（FIFO），保留最近 100 条活跃。
- 管理员可在租户设置中调整阈值（30/60/90/180 天，活跃保留数 50-500）。

**手动归档：**
- 列表页多选「归档」操作。
- 会议详情页（Explore）"⋯"菜单中「归档」选项。

**创建时预设分类：**
- 创建会议弹窗增加两个可选字段：
  - **分类/项目**（category）：下拉选择 + 可新建。从历史分类中自动补全。如 "产品规划"、"技术评审"、"竞品分析"。
  - **简写标题**（short_title）：可选，限 30 字，用于列表卡片的紧凑展示。不填则截取 topic 前 30 字。
- 这两个字段写入 `meetings.category` 和 `meetings.short_title`（新列），作为归档分组的主维度。

**决策三：归档分组策略（三层分类）**

不依赖 LLM 自动归类（不稳定、不可控、有额外成本），采用**用户自分类为主，时间+标签为辅**：

```
归档库
├── 按分类/项目（category）    ← 主维度，用户创建时指定
│   ├── 产品规划
│   ├── 技术评审
│   └── 竞品分析
├── 按时间（自动）
│   ├── 2026-Q3
│   ├── 2026-Q2
│   └── 2025-Q4
└── 按标签（tag）              ← 现有标签体系复用
    ├── 架构设计
    └── AI-Agent
```

- 归档页默认「按分类」视图，用户可切换「按时间」「按标签」。
- **不做 LLM 自动归类**：LLM 归类结果不确定，用户无法预测会议会被分到哪里，违背"可预期"原则。如未来需要，作为 P2 智能标签推荐功能（建议 tag 而非修改 category）。

**决策四：归档后图谱展示**

- 图谱页（Graph）顶部增加切换开关：「活跃会议」/「归档会议」/「全部」。
- 归档图谱默认只展示归档会议内部的节点和边，与活跃图谱隔离（避免图谱无限膨胀导致渲染卡顿）。
- 「全部」视图下，归档节点以**虚线边框 + 降低饱和度**样式区分，表示历史知识。
- 归档图谱数据走**按需加载**：切换到归档 Tab 时才请求，不影响活跃图谱首屏性能。

#### 2.3 交互设计

- **列表页 Tab**：全部 / 进行中 / 已完成 / 归档（独立 Tab，非筛选器） / 回收站。
- **归档页**：时间线式展示，左侧分类树，右侧会议卡片。卡片样式与活跃列表一致，但带「归档」角标。
- **取消归档**：归档会议的"⋯"菜单有「取消归档」，移回活跃列表。
- **创建会议弹窗升级**：topic 输入框下方增加「分类（可选）」和「简写标题（可选）」两行。
- **自动归档通知**：首次自动归档一批会议时，系统通知 + Toast："已将 5 个超过 90 天未访问的会议移入归档，可在归档库查看。"

#### 2.4 数据影响

- meetings 表新增字段：
  - `archive_status VARCHAR(20) NOT NULL DEFAULT 'active'`（active/archived）
  - `archived_at TIMESTAMP NULL`
  - `category VARCHAR(100) NULL`（分类/项目）
  - `short_title VARCHAR(100) NULL`（简写标题）
  - `last_accessed_at TIMESTAMP NULL`（最后访问时间，用于自动归档判断）
- 新增索引：`idx_meetings_archive_status`、`idx_meetings_category`。
- 访问埋点：进入 Explore 详情页、被 reference_meeting_ids 引用、被克隆时更新 `last_accessed_at`。
- 自动归档后台任务：`auto_archive_stale_meetings`（每日执行）。
- 图谱 API 增加 `archive_status` 过滤参数。

### 问题 3：同议题快速创建（克隆/重跑）与差异对照

#### 3.1 用户故事

- **US-3.1** 作为用户，上次讨论"Q4 产品规划"后有新信息，我想基于上次的结论快速重新讨论一次，不需要从头输入 topic。
- **US-3.2** 作为研究者，我对同一议题在不同模型/不同参数下跑了多次会议，希望能并排对比结论差异。
- **US-3.3** 作为团队，我们围绕"架构重构"这个话题已经讨论了 5 次，我希望看到一个统一的话题视图，展示历次讨论的演进。
- **US-3.4** 作为用户，克隆时我可以选择继承什么（议题/参会角色/历史结论/标签），不希望无脑全复制。

#### 3.2 产品决策

**决策一：区分三种"重跑"场景，产品形态不同**

| 场景 | 触发方式 | 继承内容 | 用途 |
|------|---------|---------|------|
| **克隆（Clone）** | 从已完成会议一键创建 | 用户可勾选：topic/category/tags/参会Agents配置/参考历史 | 新议题但复用上次配置 |
| **重跑（Rerun）** | 对结论不满意，重新讨论同一议题 | 继承 topic + 引用原会议结论作为输入 | 同议题重新讨论，产出新版本 |
| **追跑（Resume from stage）** | 从某阶段重新讨论（问题 4 详述） | 继承指定阶段之前的全部状态 | 对某环节不满意，局部重来 |

本次方案聚焦**克隆 + 重跑**，追跑在问题 4 中展开。

**决策二：克隆/重跑的数据模型**

引入**会议系列（Meeting Series）**概念，用 `series_id` 关联同议题的多次会议：

```
series: "s_abc123"  (topic_group 概念)
├── meeting_A (第一次，v1)  ← source_meeting_id = null, run_number = 1
├── meeting_B (重跑，v2)    ← source_meeting_id = A,   run_number = 2
└── meeting_C (重跑，v3)    ← source_meeting_id = B,   run_number = 3
```

- `series_id`：同议题多次会议共享一个 UUID（首次创建时生成，重跑/克隆时继承）。
- `source_meeting_id`：直接父会议 ID（用于构建演进链）。
- `run_number`：在系列内的序号（第几次讨论），默认 1。
- `clone_mode`：枚举 `fresh_start`（克隆，从 clarify 开始）/ `rerun`（重跑，引用父会议结论）/ `stage_resume`（追跑，从指定阶段开始）。
- 克隆 ≠ 复制数据：新会议是全新的 MeetingState，初始阶段从 clarify 开始，但通过 `reference_meeting_ids` 引用父会议结论注入 prompt，保持知识延续性。

**决策三：克隆时的继承选项**

点击「克隆」后弹出配置弹窗，用户可勾选：

- [x] **议题和描述**（topic，默认勾选，可修改）
- [x] **分类/项目**（category，默认勾选）
- [x] **标签**（tags，默认勾选）
- [ ] **参会角色配置**（agents 配置——团队成员/角色分配，默认不勾，因为重跑通常想换个思路）
- [ ] **引用父会议结论**（reference_meeting_ids 自动包含父会议，默认勾选——这是"吸取上次经验"的核心）
- [ ] **继承自定义参数**（如 flow_plan、max_iterations 等，默认折叠，高级用户展开）

点击「重跑」时，默认全选继承（因为重跑意图是"基于上次再来一次"），但跳过参会角色配置（默认使用系统推荐）。

**决策四：同话题多次讨论的展示**

**列表页展示：**
- 同一系列的会议默认**折叠为一张卡片**，显示：
  - 主标题：`Q4 产品规划`（series 最新会议的 topic）
  - 副标题：`共 3 次讨论 · 最近 2 小时前`
  - 展开后显示历次会议的时间线卡片，每个标注 `v1`/`v2`/`v3` + 结论摘要 + 状态标签。
- 折叠/展开由用户控制，列表设置中可关闭自动折叠（总是展开）。

**系列详情视图（新增页面/面板）：**
- 点击系列卡片进入「话题时间线」视图：
  - 左侧：历次会议的时间线节点（v1 → v2 → v3），每个节点标注核心结论差异点。
  - 右侧：选中某次会议的详情（复用 Explore 三栏布局）。
  - 顶部：「对比模式」按钮，选择两次会议并排对比（类似 Git diff）。

**差异对照（Diff View）：**
- 选择两个会议 v1 和 v2 后：
  - 上方：元信息对比（时间、参会角色、耗时、质量评分）。
  - 中间：结论对比——用双栏或 inline diff 展示最终产出的差异（增加/删除/修改的段落高亮）。
  - 下方：论证路径对比——两个会议的思维树/证据图谱差异。
- 差异计算：基于 artifact 的结构化字段（verdict/summary/key_findings）做语义级 diff，而非纯文本 diff（P1 实现用简单文本 diff，P2 引入 LLM 生成差异摘要）。

**决策五：reference_meeting_ids 的增强**

- 当前 reference_meeting_ids 是手动填写，克隆/重跑时自动把父会议 ID 加入该列表。
- 系列内会议引用父会议时，prompt 中注入的不是"参考历史会议 X"，而是结构化的：
  > "你是基于第 N 次讨论的重跑。上一次讨论的结论是：[结论摘要]。上次讨论中未解决的争议：[争议点]。请基于新的视角重新审视。"
- 这比通用引用更有引导性，让模型知道"这是同议题的迭代"而非"参考一个无关的历史会议"。

#### 3.3 交互设计

- **会议卡片"⋯"菜单**：增加「克隆」「重跑此议题」两个选项。
  - 「克隆」→ 弹出配置弹窗（上述勾选框）→ 创建新会议，进入 clarify 阶段。
  - 「重跑此议题」→ 直接创建新会议（默认继承配置），进入 clarify 阶段，自动引用原会议。
- **Explore 详情页顶部**：已有「克隆」按钮（如果存在），升级为「克隆」下拉菜单：克隆 / 重跑此议题 / 从某阶段重跑（见问题 4）。
- **系列折叠卡片**：
  - 卡片头部：topic + 讨论次数 + 最后更新时间 + v1→v2→v3 小时间线。
  - 点击展开：历次会议列表，每项是 mini 卡片（结论一句话 + 时间 + 质量评分）。
  - 展开态底部：「+ 再次讨论此话题」按钮。
- **系列详情页**：新的路由 `/series/:series_id`，时间线 + 对比模式。
- **Diff 对比页**：在系列详情中选择两个会议后，右侧切换为对比视图。

#### 3.4 数据影响

- meetings 表新增字段：
  - `series_id VARCHAR(36) NULL`（系列 ID，同系列多次会议共享，首次会议时生成）
  - `source_meeting_id VARCHAR(36) NULL`（父会议 ID，FK → meetings.id）
  - `run_number INT NOT NULL DEFAULT 1`（系列内序号）
  - `clone_mode VARCHAR(20) NULL`（fresh_start/rerun/stage_resume）
  - `short_title VARCHAR(100) NULL`（与问题 2 共用）
- 新增索引：`idx_meetings_series`、`idx_meetings_source`。
- API 新增：
  - `POST /meetings/{id}/clone`（克隆，带继承选项参数）
  - `POST /meetings/{id}/rerun`（重跑，简化版克隆）
  - `GET /series/{series_id}`（获取系列详情）
  - `GET /series/{series_id}/diff?base=xxx&compare=yyy`（对比两次会议）
- 列表查询改造：支持 `group_by_series=true` 参数，返回折叠结构。
- prompt 注入增强：系列内引用时注入结构化"上轮结论摘要"。

### 问题 4：从已完成会议的任意阶段重跑（追跑）

#### 4.1 用户故事

- **US-4.1** 作为用户，上次会议 cross_team 阶段双方分歧太大导致最终结论偏驳，我想保留前 3 阶段（clarify/intra_team/cross_team）的共识，但从 evidence_check 阶段重新引入新证据再讨论。
- **US-4.2** 作为用户，produce 阶段产出质量评分只有 60 分，我觉得是 arbitrate 阶段没做好，不想从头跑 30 分钟，只想从 arbitrate 重来。
- **US-4.3** 作为系统，从中间阶段重跑必须保证状态机一致性，不能出现"阶段跳跃导致 payload 缺字段"的崩溃。

#### 4.2 产品决策

**决策一：阶段重跑的本质**

当前系统已有 failed_stage + paused_snapshot 的恢复机制（从 FAILED/PAUSED 恢复），这是**故障恢复**。
"任意阶段重跑"是**用户主动回溯**，是对已完成（done）会议的某个阶段不满意，回退到该阶段的输入状态，重新从该阶段开始执行。

关键约束：
- 已完成会议（done/aborted）是**只读**的，追跑会创建一个**新会议**（不是修改原会议），保证原始数据完整可追溯。
- 新会议继承原会议从开头到指定阶段的**输入状态快照**（stage snapshot），然后从该阶段开始重新执行。
- 追跑的新会议属于同一 series（系列），clone_mode = `stage_resume`。

**决策二：哪些阶段可以作为重跑起点？**

6 个阶段不是都适合作为重跑起点：

| 阶段 | 可作为重跑起点 | 原因 |
|------|--------------|------|
| clarify | ✓ | 本质上等同于"重跑"（问题 3 的 rerun），但保留原始 topic 澄清结果 |
| intra_team | ✓ | 已有 clarified_topic 和 key_questions，重新组建团队观点 |
| cross_team | ✓ | 已有双方立场，重新进行跨团队辩论（分歧大时常用） |
| evidence_check | ✓ | 保留论点结构，重新检索/验证证据（最常用，"新证据来了"场景） |
| arbitrate | ✓ | 保留全部证据，重新仲裁（produce 评分低时的快速迭代） |
| produce | ✓ | 保留仲裁结论，重新生成产出文档（格式不满意/补充摘要） |

所有阶段都支持重跑，因为**每个阶段结束时都有原子 checkpoint**（阶段级原子持久化是系统已有能力）。

**决策三：阶段快照的存储与加载**

**当前 checkpoint 能力**：系统在每个阶段结束时持久化完整 MeetingState（payload），这意味着任意阶段结束时都有完整快照。

**追跑的数据准备流程**：
1. 用户选择原会议和重跑起点阶段（如 `evidence_check`）。
2. 系统从原会议的 payload 中提取**到该阶段开始前的状态快照**（即上一阶段结束时的 checkpoint）。
   - 例如从 evidence_check 重跑，需要 clarify + intra_team + cross_team 的完成状态。
   - 需要清理：该阶段及之后阶段产生的临时数据（如 evidence_check 产生的 evidence_set、arbitrate 的 verdict、produce 的 artifact）。
3. 基于清理后的快照创建新会议：
   - 新会议 stage 设为目标阶段（如 `evidence_check`）。
   - 状态设为 `paused`（让用户确认配置后再启动）。
   - 注入追跑上下文到 payload：`resume_from={source_meeting_id, stage: 'evidence_check', note: '引入新证据重新讨论'}`。
4. 用户确认后，新会议从该阶段开始执行 orchestrator runner。

**决策四：状态清理规则（防止数据污染）**

从 stage S 重跑时，必须清理 S 及之后阶段产生的数据，避免旧数据干扰：

| 重跑起点 | 需清理的 payload 字段 | 保留的字段 |
|---------|---------------------|-----------|
| clarify | 清空全部阶段产物，仅保留 topic/category/tags | topic, charter(?), agents config |
| intra_team | 清空 intra_team 及之后的产物 | clarified_topic, key_questions, flow_plan |
| cross_team | 清空 cross_team 及之后的产物 | 上述 + intra_team 各角色立场 |
| evidence_check | 清空 evidence_check 及之后 | 上述 + cross_team 辩论记录、争议点 |
| arbitrate | 清空 arbitrate/produce 产物 | 上述 + evidence_set、conclusion_chain |
| produce | 清空 artifact、quality_score | 上述 + arbitrate verdict |

清理规则以代码形式固化在 `stage_resume.py`（新建）中，每个阶段定义 `clear_fields` 列表。不做通用"删除所有之后字段"的模糊逻辑，必须显式枚举，避免新增字段时遗漏。

**决策五：用户确认流程**

追跑不是一键操作，因为选错起点会浪费时间：

1. 用户在 Explore 页点击「从某阶段重跑」。
2. 弹出**阶段选择器**：
   - 展示 6 个阶段的流程图，高亮已完成的阶段。
   - 每个阶段下方显示该阶段的关键产出摘要（一句话）。
   - 用户点击选择起点阶段。
3. 弹出**影响预览**：
   - 提示："将从「证据检验」阶段重新开始，保留议题澄清→团队讨论→交叉辩论的共识，重新检索证据并继续后续 3 个阶段。预计耗时 15-20 分钟。"
   - 可选：输入备注（为什么重跑，如"发现了新的关键文献"），备注会注入 prompt。
4. 点击「创建追跑会议」，新会议创建并处于 paused 状态，停在阶段选择页面。
5. 用户点击「开始执行」，runner 从指定阶段启动。

**决策六：追跑与迭代（auto_iterate）的关系**

- 现有 `auto_iterate`（最多 2 次迭代）是**系统自动**的 produce 质量不达标时的小范围重试（重新 arbitrate→produce）。
- 追跑是**用户主动**的任意阶段回溯，粒度更粗、意图更明确。
- 追跑创建的新会议仍然可以触发 auto_iterate（追跑到 produce 时评分低，仍可自动迭代）。
- 未来方向（问题 5 详述）：系统可自动建议追跑点（"evidence_check 阶段证据矛盾率 40%，是否从该阶段引入新证据重跑？"），这是自我演进的雏形。

#### 4.3 交互设计

- **Explore 页阶段时间线**：现有时间线/进度条上，每个已完成阶段增加右键/悬停菜单：「从这里重新讨论」。
- **「克隆」下拉菜单**中「从某阶段重跑」选项 → 打开阶段选择器弹窗。
- **新会议创建后**：进入一个特殊的"追跑准备页"，不是直接进入 Explore，而是展示：
  - 继承了哪些内容（前序阶段摘要列表）。
  - 将从哪个阶段开始（高亮标记）。
  - 预估时间、消耗 token 提示。
  - 「开始执行」/「取消」按钮。
- **系列视图中**：追跑会议标注特殊图标（↩ 从证据检验重跑），与普通重跑（v2/v3）区分。

#### 4.4 数据影响

- meetings 表新增字段：
  - `resume_from_stage VARCHAR(20) NULL`（追跑起点阶段，clone_mode=stage_resume 时有值）
  - `resume_note TEXT NULL`（用户输入的追跑原因备注）
  - （series_id/source_meeting_id/clone_mode 与问题 3 共用）
- 新增 `stage_resume.py` 模块：
  - 定义每个阶段的 `clear_fields` 规则。
  - 实现 `build_resume_snapshot(source_meeting, target_stage) -> cleaned_payload` 函数。
  - 实现 `create_resume_meeting(source_id, target_stage, note) -> new_meeting_id` API。
- runner 改造：支持从指定 stage 启动（不仅仅是从 clarify 开始），需要验证每个 stage 的 entry 条件满足（前置字段存在性校验）。
- 新增 API：
  - `GET /meetings/{id}/stage-snapshots`（获取各阶段快照摘要，供前端展示阶段选择器）
  - `POST /meetings/{id}/resume-from-stage`（创建追跑会议）
- prompt 注入：追跑时将 resume_note 注入 system prompt，让模型理解重跑背景。

### 问题 5：系统整体评估与自我演进路线图

#### 5.1 当前系统成熟度评估

基于代码调研和功能盘点，Conclave 当前处于**"可用的单轮讨论工具"**阶段（Beta 向 GA 过渡）：

| 能力维度 | 当前状态（0-10 分） | 评估说明 |
|---------|-------------------|---------|
| **单次会议质量** | 7/10 | 六阶段线性流程完整，质量门禁+auto_iterate 保证基本质量，checkpoint 原子持久化可靠 |
| **多轮/迭代讨论** | 2/10 | 仅有 reference_meeting_ids 弱引用，无系列/克隆/追跑，无法形成迭代闭环 |
| **知识沉淀** | 3/10 | 有图谱但仅限活跃会议，无归档/分类/项目维度，历史会议价值未释放 |
| **数据管理** | 4/10 | 有软/硬删除和恢复，但无权限模型、无归档、无回收站过期清理、列表查询性能未优化 |
| **可观测性** | 5/10 | 有 events 时间线、质量评分，但无跨会议趋势分析、无质量回归追踪 |
| **自主演进** | 1/10 | auto_iterate 是唯一的自动修正机制，但仅限 produce 阶段小循环，不会从失败中学习策略 |
| **用户体验** | 5/10 | Board/Explore/Graph/Reports 四页结构清晰，但缺系列视图、缺对比、缺归档 |

**一句话评估**：Conclave 已经是一个**能把单次多角色辩论开好**的系统，但距离"像艾克找最完美时间线一样不断重试吸取经验"的终极目标，还差**迭代闭环、知识沉淀、自我诊断**三大能力层。

#### 5.2 终极目标拆解：自我演进闭环模型

"艾克式自我演进"不是一个功能，是一个**三层闭环**：

```
                    ┌─────────────────────────────────────┐
                    │    Layer 3: 策略进化（长期）         │
                    │  系统学会"怎么开会更好"              │
                    │  - 从历史会议质量中学习参数          │
                    │  - 自动调整角色/温度/流程            │
                    │  - 发现并修复自身prompt缺陷          │
                    └──────────────┬──────────────────────┘
                                   │ 反馈策略
                    ┌──────────────▼──────────────────────┐
                    │    Layer 2: 知识进化（中期）         │
                    │  系统学会"什么结论更可靠"            │
                    │  - 跨会议结论矛盾检测                │
                    │  - 证据库积累与可信度衰减            │
                    │  - 结论被后续会议推翻则降级          │
                    └──────────────┬──────────────────────┘
                                   │ 反馈知识
                    ┌──────────────▼──────────────────────┐
                    │    Layer 1: 会议迭代（短期）         │
                    │  系统学会"这轮讨论怎么更好"          │
                    │  - 克隆/重跑/追跑（问题3+4）         │
                    │  - 系列Diff对比                      │
                    │  - 自动建议重跑点                    │
                    └─────────────────────────────────────┘
                                   │
                    ┌──────────────▼──────────────────────┐
                    │    基础层：数据管理（当前需要补）     │
                    │  删除/归档/权限/分类/性能            │
                    └─────────────────────────────────────┘
```

#### 5.3 路线图

**短期（1-2 个月）：夯实基础 + 会议迭代闭环**

目标：从"单次工具"进化到"可迭代讨论的工作台"。

| 里程碑 | 内容 | 对应问题 |
|-------|------|---------|
| M1: 数据治理 | 删除权限模型 + 回收站过期 + 列表投影查询优化 + 分类/简写标题 | 问题1+2 |
| M2: 归档上线 | 自动/手动归档 + 归档Tab + 分类视图 + 归档图谱 | 问题2 |
| M3: 克隆与系列 | 克隆/重跑 + series_id + 列表折叠 + 系列详情页 | 问题3 |
| M4: 追跑能力 | 阶段选择器 + 快照清理 + 从指定阶段启动runner | 问题4 |
| M5: Diff对比 | 两次会议结论对比（文本级 diff） | 问题3 |

短期完成后，用户可以对一个议题进行多轮迭代讨论，系统能保留历次版本并对比差异，历史会议通过归档有序管理。这是"艾克"的**回溯能力**（回到分歧点重新选择）。

**中期（3-6 个月）：知识进化层**

目标：从"迭代工具"进化到"有记忆的知识系统"。

| 里程碑 | 内容 |
|-------|------|
| M6: 跨会议矛盾检测 | 新会议结论产出后，自动检测与历史结论（同主题/相关主题）是否矛盾，标记"冲突点" |
| M7: 证据可信度系统 | 同一证据被多个会议引用，支持/反驳的结论数决定证据可信度分；被推翻的证据降级 |
| M8: 结论版本链 | 当系列内 v3 推翻了 v1 的结论，自动在 v1 上标记"已被 v3 修正"，避免引用过时结论 |
| M9: 智能重跑建议 | 系统分析质量评分、争议点、证据矛盾率，主动建议"建议从 evidence_check 阶段重跑，引入更多证据" |
| M10: 知识图谱增强 | 归档会议的结论作为"知识节点"融入图谱，支持跨会议的论点演进追踪 |
| M11: 回归分析仪表盘 | 按话题/分类展示质量趋势、迭代次数分布、常见重跑阶段（哪个阶段最容易出问题） |

中期完成后，系统不仅能让用户手动重跑，还能**主动发现哪里需要重跑**，并知道**哪些历史结论已经过时**。这是"艾克"的**学习能力**（知道哪些时间线是坏结局）。

**长期（6-12 个月）：策略进化层**

目标：从"有记忆的系统"进化到"会自我改进的讨论伙伴"。

| 里程碑 | 内容 |
|-------|------|
| M12: 参会策略学习 | 分析高质量会议的角色配置/发言轮次/温度参数，为新会议推荐最优配置（"类似话题用了3个Agent、温度0.3、质量评分92"） |
| M13: Prompt 自优化 | 当某个阶段反复触发重跑（如 cross_team 门禁通过率低），系统自动调整该阶段 prompt 模板并 A/B 测试效果 |
| M14: 自动追跑执行 | 在用户授权下，系统检测到质量问题后自动创建追跑会议（限定次数，如最多自动追跑 1 次），不需要用户手动点击 |
| M15: 多时间线并行 | 同一议题同时开 2-3 个追跑分支（不同证据集/不同视角），自动合并最优结论（真正的"艾克多时间线"） |
| M16: 元认知反思 | 每次会议结束后，系统生成"本次讨论反思报告"：哪些论据薄弱、哪些阶段效率低、下次如何改进 |

长期完成后，系统具备**策略级自我演进**：不仅讨论议题，还在讨论"如何更好地讨论议题"。这就是"艾克"的**终极形态**——不断试错、吸取经验、找到最优时间线。

## B. 功能优先级矩阵

### 优先级判定标准

- **P0（必须做，阻塞核心体验）**：不做就无法支撑日常使用，或存在数据安全/性能风险。
- **P1（应该做，显著提升体验）**：核心功能延伸，用户高频需要。
- **P2（可以做，锦上添花）**：高级功能/智能化，用户可感知但非阻塞。

### 矩阵

| 功能 | 优先级 | 理由 | 预估工作量 |
|------|-------|------|-----------|
| **删除权限模型（owner/admin RBAC）** | P0 | 无权限控制下任何人可删任何会议，安全隐患 | S（1-2天） |
| **running 状态禁止删除** | P0 | 删除运行中会议会导致 orchestrator 崩溃/资源泄漏 | XS（0.5天） |
| **硬删除二次确认** | P0 | 防误操作，不可逆操作必须确认 | XS（0.5天） |
| **回收站（deleted Tab + 恢复）** | P0 | 当前恢复功能已有但无入口，用户无法自助恢复 | S（1-2天） |

## D. 风险与边界条件

### D.1 技术风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| **追跑状态清理不完整** | 新会议 payload 残留旧阶段数据，导致阶段执行逻辑混乱或产出污染 | 1) clear_fields 显式枚举，禁止模糊匹配；2) 追跑会议启动前做 schema 校验（必需字段存在/禁用字段不存在）；3) 追跑会议增加 `_resume_meta` 标记，prompt 中告知模型这是追跑 |
| **runner 从非 clarify 阶段启动失败** | 现有 runner 假设从 clarify 开始线性执行，中间启动可能缺少初始化步骤 | 1) 每个 stage 定义 `entry_prerequisites`（前置条件检查）；2) 启动前验证前置条件，不满足则拒绝启动并给出明确错误；3) 增加 stage_resume 集成测试（6 个阶段逐一追跑测试） |
| **系列折叠导致列表查询复杂** | group_by_series 查询需要自关联或子查询，可能影响分页性能 | 1) 系列折叠在前端或应用层做（先查 N 条会议，再聚合成系列），不在 SQL 层做复杂 GROUP BY；2) 系列超过 50 个时提示用户使用归档 |
| **软删除/归档数据量过大** |  meetings 表单表数据量到 10 万+ 时查询性能下降 | 1) 部分索引（P1）；2) 冷热分离（P2）：归档超过 1 年的数据迁移到 `meetings_archive` 表；3) 列表强制分页（已有限制） |
| **自动归档误归档活跃会议** | 用户 90 天没看但仍在关注的会议被自动归档，找不到了 | 1) 自动归档前发通知（"明天将归档 5 个会议，点击保留"）；2) 被引用的会议不自动归档（reference_meeting_ids 被使用视为访问）；3) 管理员可关闭自动归档 |
| **克隆/追跑的 token 成本失控** | 用户反复重跑导致 API 费用激增 | 1) 创建追跑会议时显示预估 token/费用；2) 租户级配额限制（单议题最多追跑 N 次）；3) 自动追跑（M14）严格限制次数 |

### D.2 产品/交互风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| **用户分不清克隆/重跑/追跑** | 三个概念混淆，不知道该选哪个 | 1) 菜单文案直白化：「复制一份新讨论」（克隆）、「基于结论再讨论一次」（重跑）、「从中间步骤重来」（追跑）；2) 追跑入口收敛到阶段时间线，不在主菜单推；3) 首次使用时给轻量引导 |
| **分类/项目字段成为负担** | 用户创建会议时不想填分类，导致字段空置 | 1) 分类完全可选，不填则归入"未分类"；2) 从历史 topic 中智能推荐分类（P2，不阻塞）；3) 归档页"未分类"会议支持批量归类 |
| **系列视图过度折叠** | 用户想找某次特定会议但被折叠了，找不到 | 1) 折叠卡片展开后可见全部子会议；2) 搜索时自动展开匹配的系列并高亮匹配项；3) 列表设置中可关闭自动折叠 |
| **Diff 对比误导用户** | 文本级 diff 可能把"换种说法表达相同意思"标为差异，导致用户误判结论变了 | 1) Diff 页面顶部加提示"文本差异未必代表观点变化，请结合语义判断"；2) P2 做语义级 diff 解决此问题；3) 关键结论（verdict）单独对比，不依赖全文 diff |
| **删除不可逆操作的心理负担** | 用户不敢用硬删除，导致回收站堆满 | 1) 默认只有软删除，硬删除收到回收站二级页面；2) 30 天缓冲期足够反悔；3) 管理员硬删除权限不开放给普通用户 |

### D.3 权限与安全边界

| 边界 | 规则 |
|------|------|
| **追跑的权限** | 追跑创建新会议，新会议的 owner 是执行追跑的用户（不是原会议 owner）。原会议 owner 的会议不会被修改。 |
| **克隆的权限** | 任何能看到会议的人都可以克隆（克隆是创建新会议，不修改原数据）。租户内可克隆本租户任何非 deleted 会议。 |
| **跨租户隔离** | 所有功能严格遵守现有 tenant_id 隔离。归档/系列/追跑不跨租户。 |
| **硬删除审计** | 硬删除操作写入 events 表（审计事件），记录谁在什么时间硬删除了哪个会议。即使数据删除，审计痕迹保留（可配置保留期）。 |
| **reference_meeting_ids 引用已删除会议** | 已删除/已归档会议仍可被引用（只读）。引用已硬删除的会议时，新会议启动时提示"引用的会议 X 已被永久删除，将跳过引用"。 |

### D.4 不做的事（明确边界）

为保持聚焦，以下功能明确**不在本次方案范围内**：

1. **不做实时协作编辑**：多人同时操作同一会议（非当前架构方向）。
2. **不做会议导出为 PDF/Word 的高级模板**：Reports 页已有基础导出，不在生命周期范畴。
3. **不做 LLM 自动归类/打标签**：作为 P2 推荐功能，不做自动修改 category。
4. **不做跨租户会议共享/引用**：多租户隔离是硬边界。
5. **不做会议的评论/批注系统**：会议讨论由 Agent 完成，用户反馈通过反馈机制而非评论。
6. **不做版本控制式的分支合并（Git-style merge）**：多时间线并行（M15）是长期方向，短期不做。
7. **不做 Webhook/外部触发器触发自动重跑**：自动追跑（M14）是系统内部触发，不开放外部 API 触发。

### D.5 数据迁移与回滚

- 所有新字段均为 NULL 有默认值，迁移是** additive 的**（只加列不改列），可安全回滚。
- `payload._deleted_at → deleted_at` 的回填需要数据迁移脚本，迁移前备份 meetings 表。
- archive_status 默认 'active'，不影响现有查询逻辑。
- series_id 初始为 NULL，现有会议不受影响。
- 每个迁移脚本必须有对应的 downgrade 脚本（alembic 要求）。
