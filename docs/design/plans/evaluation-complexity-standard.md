# 代码生成产出的复杂度量化标准（讨论稿）

> **状态**：讨论稿，未定稿。基于用户 2026-07-25 讨论整理。
> **评估对象**：agent 系统的代码生成产出（非讨论产出 claim/conflict/decision）。
> **评估方式**：test suite 套件自动化，不介入人。
> **张力决策**：稳定性优先；基线稳定后可引入温度提升多样性。
> **注**：本标准暂不使用在当前项目，待沟通定稿。

---

## 0. 语境转变说明

前序讨论（见 `discussion-engine-component-autonomy.md` §1–§3）的评估对象是**讨论产出**（claim/conflict/decision/artifact），用六维复杂度向量评估。

用户在本轮把评估对象转向**代码生成产出**——用 agent 系统生成一个软件项目（如个人 Wiki），评估生成代码的质量与复杂度。这是不同维度，需要重新设计评估标准。

**核心区别**：
- 讨论产出：非结构化文本，评估"论证质量"
- 代码产出：可执行结构，评估"工程健全度"

本标准针对后者。

## 2. 三层评估框架

与讨论产出类似，代码产出也用三层框架，但指标完全不同。

### 第一层：不变性断言（硬门槛，不达标即失败）

不管生成什么代码，这些性质必须成立。可全部自动化检测。

| 指标 | 检测方式 | 断言 | 对应用户维度 |
|---|---|---|---|
| 产出结构完整率 | 检查必备产物是否存在（源码/配置/测试/README/依赖清单） | = 1.0 | 2.1 |
| 语法合法率 | `python -m py_compile` / `tsc --noEmit` / `npm run build` | 0 errors | 2.2 |
| 引用闭合性 | import/require 的模块都能解析（无 ModuleNotFoundError） | = 1.0 | 2.2 |
| 测试通过率 | 跑生成的测试套件 | = 1.0 | 2.2 |
| 测试非空率 | 测试文件数 > 0 且测试用例数 ≥ min | 满足 | 2.2 |
| 契约一致率 | API 路由定义与实现函数一一对应 | = 1.0 | 2.2 |
| 前置文档存在性 | 代码生成前是否产出了设计文档/指引（检查产物时间戳或阶段标记） | 存在 | 2.3 |

### 第二层：复杂度包络（落在区间，否则偏离）

代码产出的"复杂度"不是越大越好，也不是越小越好，而是**与需求复杂度匹配**。

**关键认知**：复杂度评估的是"生成的代码复杂度是否与需求难度一致"，不是"代码有多复杂"。简单需求产出过度复杂的代码 = 过度设计；复杂需求产出过于简单的代码 = 欠设计。两者都是缺陷。

六维代码复杂度向量：

| 维度 | 公式 | 偏低说明 | 偏高说明 |
|---|---|---|---|
| 规模 | `LOC / expected_LOC`（归一化） | 功能缺失 | 冗余堆砌 |
| 圈复杂度均值 | `avg(cyclomatic_complexity)` 归一化 | 逻辑过简（可能漏分支） | 逻辑过绕（难维护） |
| 模块化度 | `模块数 / expected_模块数`（按需求功能点） | 单文件巨石 | 过度拆分 |
| 依赖密度 | `import 数 / 模块数` | 封闭孤立 | 依赖过重 |
| 测试覆盖度 | `covered_lines / total_lines` | 测试不足 | 测试冗余 |
| 文档覆盖度 | `有文档的公开接口数 / 公开接口总数` | 文档缺失 | 文档冗余 |

**包络按需求难度分级**（easy/medium/hard 各一套区间），示例：

```
expected_complexity (medium):
  scale: [0.7, 1.3]
  cyclomatic_avg: [3, 8]
  modularization: [0.6, 1.4]
  dependency_density: [3, 10]
  test_coverage: [0.6, 0.9]
  doc_coverage: [0.7, 1.0]
```

**区间怎么定（不介入人）**：对同需求跑 N 次（如 10 次），用分位数 P10-P90 作为初始区间，积累后自动校准。

### 第三层：健全度深检 + 跨次稳定性

这一层解决用户最关心的两个问题：**测试无假绿**和**防幻觉前置文档**。

#### 3.1 测试健全度（防假绿）

"测试通过"不等于"测试有效"。假绿的常见形态和检测：

| 假绿形态 | 检测方式 | 断言 |
|---|---|---|
| 空断言 | 扫描 `assert True` / `pass` / 无 assert 的测试函数 | = 0 |
| 永真断言 | 扫描 `assert 1==1` 类 | = 0 |
| 被跳过测试 | 统计 `@pytest.mark.skip` / `it.skip` 数量 | ≤ max_skip_ratio |
| 未触达断言 | 插桩统计 assert 实际执行次数，0 次的判为未触达 | = 0 |
| 断言对象错位 | 断言的是 mock 返回而非真实行为（检查断言链是否经过真实函数） | 通过率 ≥ 阈值 |
| 变异测试存活率 | 对生成代码做小变异（改运算符/删行），跑测试，统计变异体未被测试发现的比率 | ≤ 0.3 |

**变异测试是检测假绿的最强手段**——如果改了代码逻辑测试还能过，说明测试根本没覆盖到。可集成 `mutmut`（Python）或 `stryker`（JS）。

#### 3.2 防幻觉前置文档检查

用户维度 2.3 的核心：代码生成前是否产出了约束文档。检测：

| 检查项 | 方式 | 断言 |
|---|---|---|
| 前置文档存在 | 代码产物前是否有设计文档/约束说明（按阶段时间戳或显式标记） | 存在 |
| 文档覆盖需求点 | 文档中提到的功能点 / 需求中的功能点 | ≥ 0.8 |
| 代码与文档一致 | 代码实现的模块/接口与文档描述的匹配率（名称+职责） | ≥ 0.7 |
| 边界声明存在 | 文档是否声明了"不做什么"（防跃出边界） | 存在 |
| 假设显式化 | 文档中的技术假设是否有明确列出（而非隐含） | ≥ min_count |

#### 3.3 跨次稳定性（用户决策：稳定性优先）

同一需求跑 N 次，评估：

| 指标 | 公式 | 含义 |
|---|---|---|
| 核心结构稳定性 | 多次产出的模块/接口集合的 Jaccard 相似度均值 | 核心架构应收敛 |
| 复杂度向量方差 | 六维向量跨 N 次的方差 | 复杂度不应剧烈波动 |
| 测试通过率稳定性 | N 次中测试全过的比例 | 应 ≥ 0.9 |
| 前置文档稳定性 | N 次都产出前置文档的比例 | = 1.0 |

**稳定性优先的落地**：N 次运行中，稳定性指标不达标的 case 整体判 fail，即使单次质量高。基线稳定后可放宽，引入温度提升多样性。

## 3. 评估流程（test suite 自动化）

完全自动化，不介入人：

```
1. 输入：需求描述 + 难度等级（easy/medium/hard）+ 运行次数 N
   ↓
2. 跑 N 次 agent 代码生成，收集 N 份产出
   ↓
3. 第一层（不变性断言）：每份产出都必须通过，任一失败 → 该次产出 fail
   ↓
4. 第二层（复杂度包络）：每份产出算六维向量，判是否落入对应难度的 envelope
   ↓
5. 第三层（健全度深检）：
   5.1 测试健全度（变异测试 + 假绿检测）—— 单次评估
   5.2 防幻觉前置文档检查 —— 单次评估
   5.3 跨次稳定性 —— N 次聚合评估
   ↓
6. 输出报告：
   - pass/fail（按层 + 按维度）
   - 偏离方向（哪维偏低/偏高，诊断系统行为）
   - 六维雷达图
   - 跨次趋势（复杂度是否稳定）
   - 假绿检测详情（哪些变异体存活）
```

**运行环境**：
- StubLLM 跑确定性 baseline（验证框架逻辑）
- 真实 LLM 跑非确定性评估（验证真实产出质量）
- 两者分工，前者可离线，后者依赖 LLM API

## 4. 诊断映射（偏离方向 → 系统行为）

复杂度偏离不是抽象的分数，它直接诊断 agent 系统在哪出了问题：

| 偏离 | 可能的系统问题 |
|---|---|
| 规模偏低 | 功能点遗漏，需求理解不全 |
| 规模偏高 | 过度生成，加了需求没有的东西（跃出边界） |
| 圈复杂度偏低 | 逻辑分支遗漏，没处理边界情况 |
| 圈复杂度偏高 | 逻辑绕，可能重复造轮子或没用现成抽象 |
| 模块化偏低 | 单文件巨石，没做职责分离 |
| 模块化偏高 | 过度拆分，增加理解成本 |
| 测试覆盖偏低 | 测试不足，可能假绿（测试存在但没覆盖） |
| 变异存活率高 | 测试无效，断言没真正验证行为 |
| 前置文档缺失 | 直接写代码，没防幻觉约束，跃出边界风险高 |
| 文档与代码不一致 | 代码偏离了设计，或文档是事后补的 |
| 跨次稳定性低 | agent 输出不可控，温度过高或 prompt 不稳定 |

## 5. 与个人 Wiki 场景的具体映射

用户举的 Wiki 需求（CRUD、分享、引用、提问回复、点赞统计、游客访问、时间线）作为 hard 级 case：

**需求功能点拆解**（用于计算 expected 规模）：
- 文档 CRUD（5 个功能点）
- 分享链接（2）
- 引用关系（2）
- 提问回复（3）
- 点赞统计（2）
- 游客访问控制（2）
- 时间线视图（2）
- 合计约 18 个功能点 → expected 模块数 ≈ 8-12

**envelope（hard）**：
```
scale: [0.8, 1.5]          # hard 允许略超
cyclomatic_avg: [4, 10]
modularization: [0.7, 1.3]
dependency_density: [4, 12]
test_coverage: [0.5, 0.85]  # hard 覆盖率自然低
doc_coverage: [0.6, 0.9]
```

**稳定性指标**：N 次 Wiki 生成的核心模块集合（文档模型/分享服务/时间线聚合）Jaccard ≥ 0.7。

每次跑产出不同是允许的，但核心架构（有哪些模块、关键接口）应收敛——这正好对应用户"稳定性优先"的决策。
