## 一、用户的想法（原意记录）

用户提出的架构设想：

> 每个组件和每个业务关键的封装部分，中间是依靠"引擎"进行链接的。也就是一定程度上，backend、AgentRunTime、以及各个组件都是自己维护自己的部分，包括：健康、守护、限流、扩展、并发、高并发、以及并发引起的竞争和平面节点扩展的问题。

核心诉求拆解：

1. **组件自治**：backend、AgentRunTime、各组件各自维护自身关切，不依赖中央代管。
2. **引擎链接**：组件之间通过一个"引擎"中枢进行连接与协作。
3. **自治范围**：健康检查、守护（生命周期）、限流、扩展、并发、高并发、竞争、平面节点扩展（水平加节点）。
4. **疑问**：这个想法是否合理。

## 二、Trae Design 的回复要点

### 2.1 总体判定

想法合理。该设想是业界验证过的几种架构模式的合流：

- **Erlang/OTP supervision tree**：监督树，组件挂了由 supervisor 重启
- **Actor model**：组件自治 + 消息通信
- **Cell-based（单元化）架构**：组件自治、独立扩展
- **Sidecar 模式**：关注点分离

核心思想同一句话：**组件自治 + 中央引擎做编排**。用户描述的"每个组件自己维护健康、守护、限流、扩展、并发"完全对应这些模式。

但"合不合理"需分层看，因为各关注点成本差异极大，混在一起会让"引擎"变成上帝对象。

### 2.2 关注点按成本分三档

| 档 | 关注点 | 谁来管 | 在 Conclave 栈里的落点 |
|---|---|---|---|
| 便宜 | 健康检查、生命周期守护、限流 | 组件自己 | FastAPI 健康端点 + per-component token bucket + supervisor 重启 |
| 中等 | 并发控制、竞争、高并发 | 组件自己，但用现成原语 | 已有 `lazy_asyncio` 的 LazyLock/LazySemaphore，别重造 |
| 昂贵 | 扩展、平面节点扩展（水平加节点） | 基础设施 | K8s/Redis/PG，应用代码只负责"无状态可水平扩" |

**关键判断**：第三档千万别在应用层重造。平面节点扩展的难点不在"加"，在"加完之后状态一致、租户隔离、任务不重跑、连接不串"。这些问题项目里已踩过：

- §4.1 asyncio 循环绑定
- §4.10 TRUNCATE 锁
- §4.11 xdist 数据隔离

本质上都是"多实例协作"的子问题。应用层想自己解决等于在 Python 进程内重实现分布式协调，投入产出比极差。正确做法：组件保证**无状态 + 外置状态**（PG/Redis/Qdrant），把水平扩展复杂度下放给 Docker Compose/K8s。

### 2.3 "引擎"该做什么、不该做什么

**该做（职责收窄到三件事）：**

1. **发现与路由**：组件注册、能力声明、请求分发（项目已有 event_bus，这是雏形）。
2. **监督与编排**：组件挂了重启、pipeline 阶段流转（clarify→intra_team→...→produce）、超时熔断。
3. **契约**：组件间用结构化消息（事件/任务）通信，不直接 import 对方内部模块。

**不该做：**

- 替组件管并发
- 替组件管限流
- 替组件管数据一致性

一旦引擎插手这些，组件就不自治了，退化成"引擎 + 一堆薄壳"。AGENTS.md §4.14 已点到这个坑——函数内 import 滥用的反面就是"什么都往中央塞"。

### 2.4 两个现实约束

**约束一：asyncio 是单进程的。**

单进程内谈"组件自治"，自治是逻辑隔离，不是物理隔离。一个组件崩了（OOM、死循环）会拖垮同进程所有组件。真正进程级隔离要靠多容器/多进程。所以"组件自治"在单进程内能做到的上限是：**逻辑边界清晰 + 异常隔离 + 资源配额**，再往上就得拆进程。"守护/重启"在单进程内只能是 try/except + supervisor 重置状态，不是 OS 级守护。

**约束二：Conclave 是 CPU/IO 混合的 agent 系统。**

LLM 调用是 IO 密集（asyncio 友好），但 evidence_check、embedding、arbitrate 里有 CPU 计算。纯 asyncio 会被 CPU 段阻塞。"高并发"这一档迟早要引入进程池（`run_in_executor`）或独立 worker。这正好是"平面节点扩展"的天然切口——把 CPU 密集阶段拆成独立 worker 集群，asyncio 主进程只做编排。

### 2.5 分层判定

| 设想部分 | 判定 | 说明 |
|---|---|---|
| 组件自治（健康/守护/限流/自身并发） | ✅ 应用层做 | 成本低，收益直接。对应已有 lazy_asyncio、event_bus、单例循环感知 |
| 引擎做薄（发现/编排/监督/契约） | ✅ | pipeline orchestrator + event_bus 已是胚胎 |
| 水平扩展/平面节点扩展 | ⚠️ 交给基础设施 | 应用只保证无状态 + 外置状态，别在 Python 里重造分布式协调 |
| 竞争/高并发 | ⚠️ 用现成原语 | Lock/Semaphore/Queue + 连接池，别自己写。§4.1 循环绑定坑已证明代价大 |

## 三、待定问题（后续继续讨论）

### 3.1 核心边界问题（最优先）

**AgentRunTime 和 backend 是同进程还是分进程？**

- 同进程：自治上限是逻辑隔离
- 分进程：要真隔离（独立扩展、独立重启、资源不互相挤），"引擎"从进程内 event_bus 升级成跨进程消息总线（Redis Stream / NATS）

这个选择直接决定后面所有架构决策，需先想清楚。

### 3.2 用户对"引擎"的进一步澄清（补充）

> 我说的引擎，即某一层组件的对外出口，即网关？大概类似于对外的唯一 api 层？类似的概念。但这样的话可能需要每一层都有一个 fastapi？这样有点扯。

**用户的收敛**：把"引擎"理解为"某一层组件的对外出口 / 网关 / 唯一 API 层"。

**用户自己的质疑**：如果每层都要一个 FastAPI，太重了，"有点扯"。

**Trae Design 的判定（见下方 §二补充）**：

- "引擎 = 网关"这个理解**部分正确但范围过窄**。网关只是引擎三职责（发现路由 / 监督编排 / 契约）中的"发现路由"的一部分。
- "每层一个 FastAPI"是**典型的过度具象化陷阱**——把"对外出口"等同于"起一个 HTTP 服务"。出口的形态取决于调用方，不必须是 HTTP。
- 正确做法：**出口形态跟着调用方走，不跟着"层"走**。同进程用函数调用，跨进程用 RPC/消息，对外才用 HTTP。一个系统里通常只有最外层需要 FastAPI。

### 3.3 用户对并发问题的追问（补充）

> 涉及到并发有几个问题：幂等性、唯一性、消息重复消费、消息失败回滚、以及死信队列等等。各种各样的问题，我们到最后都肯定要依赖于 redis stream 或者 mq 之类的组件？

**用户的倾向**：认为这些并发问题最终必然依赖 Redis Stream / MQ 之类的中间件。

**Trae Design 的判定（见下方 §2.6）**：

- 这个判断**不成立**。这五个问题里，只有死信队列是 MQ 的原生能力，其余四个的解法都在应用层/数据库层，MQ 不是解法，反而是部分问题的来源。
- 关键认知：**MQ 引入的是"最终一致性"，换来的是脆弱性增加（多故障点）、调试变难、运维变重**。不是"将来要用就提前上"。
- 正确的引入时机：决定拆进程/拆服务的那一刻，且确实需要"可靠投递 + 消费确认"时。在那之前，PG 事务 + 唯一约束 + asyncio 原语够用。
- Conclave 的 pipeline 是同步编排（clarify→intra→...→produce），不是事件驱动，强行上 MQ 是过度设计。

### 3.4 待展开的子话题

- 组件自治的具体边界：每个组件的"自治接口"长什么样（健康/限流/并发配额如何声明）
- 引擎的契约层：事件 schema、组件注册协议、监督策略（重启次数/退避）
- **出口形态选择**：每层组件的"对外出口"该用什么形态（函数调用 / RPC / 消息 / HTTP），如何避免"每层一个 FastAPI"的过度具象化
- **并发五问的解法分层**：幂等性/唯一性/重复消费/失败回滚/死信队列，各自该在应用层、数据库层、还是 MQ 层解决
- **MQ 引入时机判定**：什么场景下才真正需要 Redis Stream / MQ，Conclave 现阶段是否需要
- CPU 密集阶段拆 worker 的切口选择（evidence_check / embedding / arbitrate 哪个先拆）
- 外置状态的边界：哪些状态必须外置才能支持水平扩展，哪些可保留进程内
- 与现有 event_bus / pipeline orchestrator 的演进路径（渐进式 vs 重构）

### 3.5 用户对幂等方案的追问（补充）

> 高并发高频导致的重复消费问题，常规手段已经失去效力。我能否将事件的入口 id（类似 trace id）当作入锁的 key 存入队列，且这个 key 只能被消费一次？key 后面对应阶段，根据 key 和阶段去判断如何？

**用户的方案**：trace_id 作去重 key → 入队列 → key 只能被消费一次 → key 关联阶段 → 按 (key, 阶段) 判断如何处理。

**Trae Design 的判定（见下方 §2.7）**：

- 方向正确，trace_id 作幂等键是行业标准做法。
- 但"存入队列且只能消费一次"这个描述混了两个不该混的东西：**"去重"和"排队"是两件事**。去重用 SETNX/唯一约束，排队用队列；把去重塞进队列会让队列同时承担两个职责，反而更脆。
- 正确拆分：**去重 key 用独立存储（Redis/PG），队列只管投递**。先查 key 存在性 → 存在则丢弃 → 不存在则加锁标记 + 入队。
- "key 后面对应阶段"这个设计是对的——去重粒度应是 (trace_id, stage)，不是 trace_id 单独。同一 trace_id 跨阶段要允许，同阶段重复才挡。
- 关键陷阱：**锁必须带 TTL + 处理结果状态机**，否则处理中崩溃会留下僵尸锁，后续全部被误挡。
- Conclave 落点：用 Redis 的 `SET key value NX EX ttl` 做单 key 去重，value 存 `{stage, status, result_ref}`，比自造队列轻得多。

### 3.7 用户对阶段推进原则的洞察（补充）

> 我的想法是，我们这个系统不管如何，无论是哪个管道阶段，只要走一步永远是 n+1，这样才算是不会导致 stage 重复的吧。

**用户的洞察**：阶段推进必须严格前移 n→n+1，这是防止 stage 重复的根本机制，比 trace_id 去重更本质。

**Trae Design 的判定（见下方 §2.8）**：

- 这个洞察**正确且更根本**。它点出"stage 重复"有两种不同成因，要分开：
  - **成因 A：已完成阶段被重新触发** → 由状态机 n+1 规则挡住（current_stage 已前移，旧 stage 无法重入）
  - **成因 B：同一阶段被并发请求同时启动** → 由 trace_id+锁串行化（两个请求同时看到 current_stage=n，都要启动）
- n+1 状态机是**主防护**，trace_id 锁是**并发补防护**，两者解决不同问题，不是二选一。
- **关键修正**：Conclave 的 pipeline 不是严格线性。"永远是 n+1"是默认规则，但有三种合法的非前移转移必须显式处理：
  - clarify 循环回到 clarify（用户补充澄清）
  - intra_team supplement 模式（补角色，同阶段内扩展）
  - cross_team 回流 intra_team（§4.21 提到的场景）
- **失败重试**：失败状态允许同阶段重试（n→n），但必须记 attempt 计数防无限重试。成功状态才强制 n+1。
- **落地**：状态机的转移规则要写成显式白名单（允许的 from→to 对），而不是"只允许 +1"的简单规则。

## 五、方案待完善的 6 个问题（归档，后续一并讨论）

> 以下 6 个缺口由 Trae Design 自审发现，用户指示归档，待后续继续讨论时一并沟通。

### 5.1 trace_id 的生成与信任边界未定义

- 客户端传还是服务端生成？被伪造怎么办？
- 跨服务传播如何保证不丢？
- 未定义则无法防恶意重放

### 5.2 状态机与锁的释放顺序有窗口期

- 先释放锁还是先前移状态？
- 先释放锁 → 另一请求拿到锁但状态没前移 → 重复执行
- 先前移状态再释放锁 → 状态前移失败但锁占用 → 僵尸
- 需要：状态前移成功后再释放锁，且前移用乐观锁原子完成

### 5.3 长事务的 TTL 问题

- 一次 agent 会议可能跑几十分钟，trace_id 锁 TTL 设多少？
- 太短误释放，太长僵尸
- 需要锁续期机制（watchdog），又增加复杂度

### 5.4 异常退出路径缺失

- 状态机白名单只覆盖正向转移
- 没定义取消/中止/超时/降级的转移
- 用户主动取消、超时熔断后状态怎么走？没定义会卡中间态

### 5.5 失败重试阈值应 per-stage

- clarify 失败便宜，arbitrate 失败贵
- 全局统一阈值不合理，要按阶段成本配置

### 5.6 组件间共享状态归属未定义

- 两个组件都要读写同一状态，归谁管？
- 需要状态所有权矩阵，否则出现"谁都以为对方管"的真空
